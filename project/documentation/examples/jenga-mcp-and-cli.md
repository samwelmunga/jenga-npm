# Jenga MCP Router & CLI — Concept Explanation

> Generated by `/examplify` on 2026-05-09 · Updated 2026-05-10 (E15, E16_S04)

---

## 1. What it is

The **Jenga system** is a two-part framework that makes skill-based prompt routing **automatic and transparent** inside Claude Code (or any AI coding agent):

- **`mcp/router/index.js`** — a Node.js stdio MCP server (the "brain"). It is auto-spawned by the AI client (e.g. Claude Code) when a session opens, holds a live index of your skills, and decides what to do with every prompt: invoke a skill or pass through unchanged.
- **`bin/jenga.js`** — a CLI tool (`jenga init / attach / status`) that wires everything together: creates the config, registers the router as an MCP server in both the project's `.claude/settings.json` (Claude Code) and `.agents/settings.json` (GitHub Copilot CLI), and shows its health.

Each project maintains its own router state under `.jenga/` (gitignored), so multiple projects can run simultaneous router instances without conflict.

---

## 2. Why it exists

Without Jenga, you invoke skills *manually* — you type `/brainstorm`, `/do`, `/commit`, etc. Jenga makes that **automatic**: you type natural language and the router figures out which skill (if any) to invoke.

It also solves the **session problem**: once a skill is running, follow-up messages should go *into* the skill session, not re-trigger a new match. Jenga tracks that too.

## 3. How it works

### Full prompt flow

```
User types a prompt in Claude Code
         │
         ▼
  hooks/prompt_router.sh   ← UserPromptSubmit hook (Claude Code calls this)
         │
         ▼
  prompt_router_helper.js  ← Checks if router is running via <cwd>/.jenga/router.pid
         │
    ┌────┴──── router not running? ──► passthrough (original prompt unchanged)
    │
    ▼
  mcp/router/index.js  ← Jenga Router (stdio MCP server, auto-spawned by AI client)
         │
    route_prompt(text)
         │
    Stage 1: starts with "/"? ──► passthrough
         │
    Stage 0: session active? ──► passthrough + reset inactivity timer
         │
    Stage 2: keyword match?
         │      scores skill name + keywords + examples
         │      confidence ≥ threshold (default 0.75)?
         │
    ┌────┴──── yes ──► action: "invoke"
    │                  transformed: "/brainstorm let's plan auth"
    │                  sets activeSession = { skill: "brainstorm", ... }
    │                  starts 5-min auto-expire timer
    │
    └──── no ───► action: "passthrough"
         │
         ▼
  Hook outputs transformed prompt to Claude Code
         │
         ▼
  Claude Code sees: "/brainstorm let's plan auth"
  and invokes the brainstorm skill automatically
```

### Project-scoped state

Each project gets its own `.jenga/` directory (gitignored) for runtime state:

```
<project-root>/
  .jenga/
    router.pid      ← PID of the running router process
    session.json    ← active skill session (if any)
```

This means two projects can run their routers simultaneously without conflict. `jenga status` reads from `<cwd>/.jenga/` so it always reflects the router for the project you're currently in.

### Router lifecycle

```
jenga attach  →  writes mcpServers.jenga entry into .claude/settings.json
                 and .agents/settings.json
                 ↓
AI client opens session  →  auto-spawns router via stdio MCP
                 ↓
invoke → activeSession set → follow-ups pass through → skill emits
[JENGA:SESSION_END:brainstorm] → session_end_watcher.sh calls end_session()
→ router clears session → normal matching resumes
                 ↓
AI client closes session  →  router process exits, PID file removed
```

### Skill index

Built at startup from `SKILL.md` frontmatter across the skills directory:

```js
{
  name: "brainstorm",
  description: "Engage the scrum-master agent...",
  keywords: ["brainstorm", "plan", "ideate", "feature planning"],
  examples: ["let's brainstorm ideas for X", "I need to plan a new feature"],
  path: "/path/to/skills/brainstorm/SKILL.md"
}
```

### Matching score example

For prompt `"let's plan a new authentication feature"` against `brainstorm`:
- keyword `"plan"` match → +0.7
- keyword `"feature planning"` partial → +0.35
- example word overlap → +0.25
- normalized confidence ~0.77 → **above 0.75 threshold → invoke**

## 4. When to use it

| Use Jenga when… | Don't use Jenga when… |
|---|---|
| You want natural-language skill invocation | Your team always types `/skill` manually |
| You have many skills and can't remember them all | You have only 1–2 skills |
| You want session tracking (follow-ups stay in skill) | You're building a non-Claude-Code agent |
| You want `jenga attach` to handle all wiring | You need vector/semantic matching (keyword-only for now) |
| You work across multiple projects simultaneously | — |

## 5. Examples

### Example A — First-time setup

```bash
$ jenga init
Welcome to Jenga! Let's set up your configuration.

Agent target options: claude, copilot, custom
Agent target (default: claude): claude
Skills directory path (default: skills/): skills/
Match confidence threshold (0–1) (default: 0.75): 
Session timeout (minutes) (default: 5): 

✓ Configuration written to jenga.cli.json
✓ Hook registered in settings.json
✓ .jenga/ added to .gitignore

Run `jenga attach` to register the router with your AI client.

$ jenga attach
Attached. Open a new session in this project to start routing through Jenga.
  ✓ .claude/settings.json updated
  ✓ .agents/settings.json updated

$ jenga status
✓ Router running (PID: 48291) | No active session
```

> **Note:** The router is started automatically by the AI client (e.g. Claude Code or GitHub Copilot CLI) when it opens
> a new session — there is no `jenga start` command. `jenga attach` writes the MCP server entry
> into `.claude/settings.json` and `.agents/settings.json` once; every subsequent session
> auto-spawns the router via stdio.
> Running `jenga status` right after a session opens will show "No active session" — this is
> expected. An active session only exists while a skill invocation is in progress.

### Example B — Automatic skill dispatch

```
# User types (no slash!):
"let's brainstorm ideas for the onboarding flow"

# Router scores → brainstorm matches at 0.82 confidence
# Hook rewrites prompt to:
"/brainstorm let's brainstorm ideas for the onboarding flow"

# Claude Code invokes /brainstorm automatically
# activeSession = { skill: "brainstorm", startedAt: "2026-05-09T..." }

# Follow-up: "what about email verification?"
# Stage 0 fires → passthrough (stays inside brainstorm session)

# Brainstorm concludes, emits:
[JENGA:SESSION_END:brainstorm]

# session_end_watcher strips the marker, calls end_session("brainstorm")
# Normal matching resumes
```

```json

Running `jenga attach` again is safe — it overwrites the `"jenga"` key in both config files with the current router path (useful after upgrading Jenga).

```
